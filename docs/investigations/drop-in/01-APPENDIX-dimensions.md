### Switch notes
For the runtime-swap switch, sessions/cookies/CSRF is the dimension that most argues for sharing state with the existing bench rather than reinventing it. The clean design: ferro reuses Frappe's EXISTING session store. Because the bench site is SQLite (sites/mysite.sqlite) and ferro already opens it, ferro can read/write tabSessions directly using Frappe's exact schema and sid format (56-hex token, sessiondata JSON incl csrf_token). That makes sessions interoperable in BOTH directions: a session minted by CPython resumes under ferro and vice-versa, which is essential if the switch is per-route or a gradual rollout, or if a fallback to CPython is kept. The cache layer (frappe.cache.hset('session',...)) is a Redis optimization; ferro can skip Redis and go straight to the DB (Frappe already falls back to DB on cache miss, sessions.py:353-357), so the switch does NOT require Redis. WHAT STAYS PYTHON: nothing structurally must — but the password-hash long tail (argon2, passlib needs_update rehash, 2FA via twofactor.py, OAuth bearer via oauthlib, LDAP, auth_hooks, login attempt tracking) is realistically Python: route /api/method/login (and the few auth hooks) to ferrod's embedded CPython or leave login on the CPython worker, while ferro handles the high-volume RESUME + CSRF-validate + per-request identity-from-sid path purely in Rust. WHAT BECOMES FERRO: cookie parsing, sid->user resolution from tabSessions, CSRF compare, and the API-token/Basic path (already done in auth.rs+crypto.rs). The switch knob is therefore: 'identity resolution from the sid cookie' moves to Rust (reading the same tabSessions Frappe wrote), and only credential-MINTING (login/2FA/oauth) optionally stays Python. The browser/desk side needs nothing changed: it only requires (a) the sid cookie present and round-tripped, (b) the non-HttpOnly identity cookies for the navbar, and (c) frappe.csrf_token rendered into desk.html to match what the server validates — all server-internal, all reproducible by ferro against the shared DB.

### Python boundary
MUST stay Python (or ferrod embedded CPython), at least initially: credential MINTING and its long tail — 2FA (frappe/twofactor.py), OAuth bearer issuance/verify (frappe/oauth.py + oauthlib), LDAP, argon2 password hashes, passlib needs_update rehash-on-login, login-attempt lockout, and arbitrary auth_hooks (auth.py:752). These are one-time-per-login and low-volume, so routing /api/method/login (and OAuth endpoints) to CPython while ferro owns everything else is acceptable. CAN/SHOULD be ferro (pure Rust, high-volume per-request path): parsing the Cookie header, resolving sid->user via the shared tabSessions table (no Redis needed — DB fallback exists), CSRF token compare on unsafe methods, setting/refreshing cookies, and the API-key:secret + Basic + Fernet path (already implemented in auth.rs/crypto.rs). pbkdf2_sha256 password verification for the common login case is also feasible in pure ferro using existing crypto.rs primitives if avoiding the CPython hop is desired. The hard requirement for drop-in correctness is that ferro reads/writes the SAME sid+csrf+sessiondata format Frappe uses, so sessions interoperate with the existing bench.

### Switch notes
This dimension is the clearest place where the runtime-swap switch must distinguish a small one-time Python boundary from the per-request hot path. ### Switch notes
This dimension splits cleanly along the runtime-swap switch into THREE layers, each with a different home:

LAYER A — Static assets (/assets, /files): in PRODUCTION this layer does not belong to either runtime — nginx serves it directly (nginx.conf:57-59, 84-89) and bypasses gunicorn entirely. So the switch should leave nginx untouched; ferro need not serve /assets at all in prod. The 'relevant modification' is zero for assets in prod. In DEV (`bench serve`) the chosen runtime must serve assets; pure ferro already does the desk subset (desk.rs:256-274) and just needs ETag/304/+/files for full dev parity. RECOMMENDATION: make the dev switch point `bench serve`'s web entry at ferro, and document that prod relies on nginx as today.

LAYER B — The desk SPA shell (/desk, /app): this is the high-value, low-coupling target. The shell is one Jinja template (www/desk.html) + a boot blob. Pure ferro can own this end-to-end IF it (1) renders the real www/desk.html via minijinja instead of a hand-copied format! string, and (2) builds boot from the live ORM/meta it already has. This is the part of 'Jinja' that genuinely can be pure-ferro because the template uses only ~10 globals (include_script/style/icons + orjson_dumps of boot). STAYS FERRO.

LAYER C — Arbitrary website/portal pages (path_resolver + TemplatePage/DocumentPage/WebFormPage/ListPage, DB-stored Web Page/Web Form/Web Template with server-side get_context and sandboxed Jinja exec): this is irreducibly Python-coupled. Templates can run arbitrary frappe.* API in Jinja (safe_exec get_safe_globals, 911 lines) and doctype controllers' get_context. Reimplementing that surface in Rust/minijinja is a rewrite, not a shim. RECOMMENDATION for the switch: route all non-/desk, non-/api, non-/assets requests to the embedded-CPython path (ferrod) calling frappe.website.serve.get_response unchanged. So the switch is: ferro handles /api (data plane) + /assets (dev) + /desk shell; ferrod (or upstream-Python fallback) handles the website layer. A pure-ferro-only deployment must declare website pages out of scope in v1.

Net: the switch is NOT 'all website rendering becomes ferro'. It is 'data plane + asset serving + desk shell become ferro; the website/Jinja long tail stays Python (via ferrod or a passthrough)'. The orchestration switch should expose a capability flag so a site with no public website can run pure-ferro, while a site with portal pages keeps the CPython website renderer alive behind the same process.

### Python boundary
MUST stay Python (runtime): the general website renderer (path_resolver + DocumentPage/WebFormPage/ListPage), any www/*.py get_context module, DB-stored Web Page/Web Form/Web Template Jinja (which can execute arbitrary frappe.* via the sandbox), and the full frappe.* Jinja globals/filters long tail (safe_exec.get_safe_globals). CAN be ferro (runtime): static asset serving for /assets and /files (pure Rust file server with ETag/304 — already 90% done for /assets), the /desk and /app shell render (minijinja over the real www/desk.html + a live-built boot), and simple static www/*.html TemplatePages that have no get_context and no DB dependency. The pure-ferro/ferrod fork line is exactly the get_context / DB-doc / sandboxed-Jinja boundary: no-Python-needed templates -> ferro; any-Python-needed template -> ferrod.

## Socket.IO / realtime  —  verdict=yellow (5%)

**Effort:** M — Tier 1 (get_user_info + has_permission + sid/tabSessions session + secret skip) is S-to-M and unblocks connection; Tier 2 (write-only Redis PUBLISH of list_update/docinfo_update on ORM writes) adds a small RESP client, pushing it to M. Both are bounded, no new architecture; the only hard line is that server push is impossible without touching Redis.

### How Python does it
Realtime is a SEPARATE Node process, not part of the WSGI worker. Procfile line `socketio: /usr/bin/node apps/frappe/socketio.js` (/home/frappe/benches/bench-cpython314/Procfile) launches it; it listens on socketio_port 9000 (common_site_config.json) and is unaffected by what serves Python requests. Flow:
1) BROWSER connects: socketio_client.js:53/60 does `io(host + "/" + frappe.boot.sitename, {withCredentials:true})` — multitenant namespace = the site name, browser cookies (incl `sid`) ride along via withCredentials.
2) NAMESPACE: index.js:23 `io.of(/^\/.*$/)` accepts any site as a namespace; authenticate.js:13-19 validates namespace == site name and 21-24 validates host==origin.
3) AUTH (the critical drop-in contract): authenticate.js:35-42 parses the `sid` cookie (or Authorization header), then 67-82 calls back into the PYTHON web app over HTTP: `GET {origin}/api/method/frappe.realtime.get_user_info`, forwarding `Cookie: sid=<sid>` (authenticate.js:54-55) plus header `X-Frappe-Socket-Secret: <secret>` (authenticate.js:57-60). The secret is read from Redis key `socketio_auth_secret` on the redis_queue connection (authenticate.js:5-11).
4) get_user_info (frappe/realtime.py:142-156, @whitelist(allow_guest=True)): resolves `frappe.session.user` from the sid (sessions.py:359-393: Redis `session` hash, DB fallback to `tabSessions(sid,user,sessiondata,lastupdate)`), compares provided `X-Frappe-Socket-Secret` to `get_socketio_secret()` (realtime.py:127-139, generated and stored in redis_queue), returns `{}` on mismatch, else `{user, user_type, installed_apps}`. socketio.js stores these on the socket (authenticate.js:79-81).
5) ROOMS: handlers.js joins `user:<user>` and `website` on connect, `all` for System Users (4-10). Subscribe events doctype_subscribe/doc_subscribe/doc_open are permission-gated via a SECOND HTTP callback `GET /api/method/frappe.realtime.has_permission?doctype=&name=` (handlers.js:12-27 -> realtime.py:118-121) before joining `doctype:<dt>`, `doc:<dt>/<dn>`, `open_doc:<dt>/<dn>` rooms (handlers.js:144-148).
6) SERVER->CLIENT push: Python `publish_realtime`/`emit_via_redis` (realtime.py:23-115) PUBLISHes JSON `{event, message, room, namespace=site}` to Redis channel `events` on the no-auth redis_queue conn (background_jobs.py:616). socketio.js subscribes to `events` (index.js:73-87) and relays `io.of("/"+namespace).to(room).emit(event, message)`. This is how list_update/docinfo_update/msgprint/progress reach the browser; e.g. document.py:1824-1844 calls publish_realtime("list_update", after_commit) on every save.

### Ferro state today
ferro currently provides nothing for realtime: no get_user_info (main.rs:490-497, desk.rs:351-413), no has_permission method, no sid/session resolution (auth.rs:37-79 token-only; login sid is cosmetic, main.rs:370-392), no Redis, and no event publishing on ORM writes (orm.rs). ### Switch notes
socketio.js is a node process owned by the Procfile and is NOT part of the runtime swap — it stays byte-for-byte identical whether CPython or ferro serves web. The swap point is purely the HTTP callbacks socketio.js makes into the web app (get_user_info, has_permission) plus the Redis `events` channel that the web app publishes to. So the switch only has to guarantee two things on the ferro side: (1) ferro answers those two whitelisted endpoints with the same JSON shape, and (2) something publishes write events to Redis channel `events`. There is a clean tiered design: TIER 1 (client->server connectivity, ~150 lines pure-ferro, no Redis): implement get_user_info + has_permission + sid->session via tabSessions in SQLite; ignore the socket secret. This makes the socket CONNECT and rooms join, but nothing is pushed. TIER 2 (server push, +~50 lines, write-only Redis): ferro PUBLISHes list_update/docinfo_update to channel `events` after ORM writes — no SUBSCRIBE, no read, so Redis stays a fire-and-forget output. With Tier 1+2, socketio.js runs unmodified and realtime is functionally complete for the common cases (auto-refresh lists/forms, msgprint, progress, doc_viewers). What MUST stay infrastructure: the Redis server (already in the bench's Procfile/common_site_config redis_queue 11000, redis_socketio 13000) and the node socketio process. What can be ferro: both whitelisted endpoints and the publish side. The escape hatch distinction matters: ferrod (embedded CPython) could just expose real frappe.realtime.* and frappe.publish_realtime, getting full fidelity for free but at framework memory cost; pure-ferro needs the ~200 lines above and CANNOT do server push at all if it refuses Redis entirely (Tier 2 is the irreducible Redis dependency for push).

### Python boundary
MUST stay infrastructure (not ferro): the node socketio.js process (Procfile-owned, unmodified) and a running Redis (redis_queue/redis_socketio already in common_site_config.json). MUST be served by ferro when swapped: the two whitelisted HTTP endpoints frappe.realtime.get_user_info and frappe.realtime.has_permission (these move from Python to ferro because socketio.js calls them against whatever serves web). CAN be ferro (and should, for any live updates): publishing write events to the Redis `events` channel. ### Blockers
- **[high] SQLite WAL coexistence: ferro and Python workers share one .db with incompatible journal modes**

In a drop-in, ferro is the web tier but bench worker/schedule still write to the same SQLite file.

### Switch notes
Two-tier dispatch is the whole story for the runtime swap. TIER 1 (native, no Python): the hot ~30 boot+list+read methods are already in desk::route_method (desk.rs:339-410) and are drop-in -- a flipped switch serving desk traffic gets a working boot, list view, and read-only form immediately. Add ~6 more native arms (savedocs->ORM, search_link/search_widget->ORM LIKE, real docinfo, get_count edge cases, user_settings persist, translations) and you reach a genuinely USABLE desk (boot+list+form+save+search) entirely in Rust for pure-CRUD doctypes -- this is ~36 native methods vs 30 today, i.e. ~6 to build. TIER 2 (CPython fallback) is REQUIRED for the long tail (run_doc_method, report run, share/assign/tag/follow, upload_file, email, the 100+ remaining) and for save on doctypes with controller lifecycle. The fallback MUST be the bench's existing CPython+Frappe app code reached via embedded interpreter -- this is exactly ferrod's model, but ferrod today only wires the WRITE-hook half (dispatch_write). The switch design: route /api/method -> try native arm; on miss, if ferrod is the active binary, call a NEW ferro_boot.dispatch_method(cmd, form_dict, user) mirroring handler.execute_cmd (get_attr+is_whitelisted+frappe.call). Crucially, is_whitelisted MUST be enforced in the fallback to keep the security boundary the real handler provides. So the switch is: pure-ferro binary = native-only (boot+list+read+pure-CRUD save), good enough for simple sites; ferrod binary = native fast-path + CPython fallback, full fidelity. The Python boundary is one-time at boot (import controllers, build whitelist registry) plus per-request only for tail methods; the hot path stays GIL-free Rust.

### Python boundary
MUST stay Python (runtime, via ferrod embedded CPython fallback): arbitrary whitelisted controller logic -- run_doc_method, report run_report, server scripts, upload_file (file processing), email send, share/assign/tag/follow side effects, setup_wizard, and document save/submit for any doctype carrying validate/before_save/on_update/on_submit. These are open-ended Python and cannot be reimplemented natively per-method at scale. ONE-TIME Python (boot): importing app controllers and building the whitelist + needs-python registry (ferro_boot.load, already done). CAN be ferro (native, no Python): the entire boot read set, list view (reportview.*), form read (getdoctype/getdoc/docinfo), client.get*/get_value/get_count/get_single_value, search_link/search_widget (ORM LIKE), user_settings persistence, translations, and document save for PURE-CRUD doctypes (no controller hooks -- the registry already identifies these). Net: ~53% of doctypes are pure-CRUD per prior memory, so a large fraction of saves never need Python; the fallback is for the controller-bearing minority plus the genuinely-Python method tail.
